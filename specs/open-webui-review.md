## Recommended first rollout: keep the native service and keep it chat-only

1. Choose a package pin and stage against separate, private state before moving production. Check [security advisories](https://github.com/open-webui/open-webui/security/advisories) before choosing a release: post-0.11.4 releases include security fixes; for example [GHSA-3vvh-g22g-jq6r](https://github.com/open-webui/open-webui/security/advisories/GHSA-3vvh-g22g-jq6r) lists versions below 0.12.2 as affected. Back up writable state and preserve the existing secret configuration securely. If using stock SQLite, stop the service for a consistent full data copy or use a SQLite-safe backup; a Nix generation rollback alone will not undo schema migrations. If using an external DB or storage, back those up too. See [backup docs](https://docs.openwebui.com/tutorials/maintenance/backups/).
2. Keep `chat.bepis.lol` on Nginx and loopback upstream. HTTPS, HTTP/1.1 WebSocket upgrades, 200 MiB upload limit and 600-second proxy read/send timeouts are already configured through [`hostedServices`](../modules/hosted-services/server.nix). Add explicit **`proxy_buffering off;` for this vhost's `/` location** if making the recommended streaming configuration; existing `proxy_request_buffering off;` only affects uploads. Check actual token streaming and WebSocket reconnect. For public hosting, verify signup is closed or approval-only, pin `CORS_ALLOW_ORIGIN` to the site, keep authentication on, and disable unused code execution and in-process plugins. If only tailnet users need it, consider switching the vhost to tailnet-only separately. See [proxy](https://docs.openwebui.com/troubleshooting/performance/), [environment](https://docs.openwebui.com/reference/env-configuration/) and [hardening docs](https://docs.openwebui.com/getting-started/advanced-topics/hardening/).
3. Keep the current general LiteLLM Chat Completions connection. The installed 0.11.4 source (`open_webui/routers/openai.py`) already has a per-connection Responses mode and a model ID list. Test a second connection to the same LiteLLM `/v1` with only the two `sub-gpt-6.2-*` aliases in Responses mode. Avoid duplicate model IDs across the general and subscription connections (filter/prefix as needed), don’t globally flip the mixed catalog, and check key/model permissions before switching. Test two turns, streamed text, reasoning and any intended tool calls; keep image generation on its separate `/images/generations` connection. Test image generation and web search after migration. See [Open Responses setup](https://docs.openwebui.com/getting-started/quick-start/connect-a-provider/starting-with-open-responses/).
4. Verify existing logins, chats, uploads/knowledge and model visibility before and after migration. Review effective Admin settings explicitly; `ENABLE_PERSISTENT_CONFIG=false` is a broader policy choice, not a one-off image-setting fix. Keep a single instance with local storage for this scope. PostgreSQL/Redis/shared storage are not required for a routine upgrade; revisit them for multiple replicas or a specific need such as cross-instance session revocation. See [scaling docs](https://docs.openwebui.com/getting-started/advanced-topics/scaling/).

For the NAS RAG integration, [`rag-mcp-server.py`](../modules/services/rag/rag-mcp-server.py) currently serves legacy SSE. Open WebUI's [native MCP connector](https://docs.openwebui.com/features/extensibility/mcp/) uses Streamable HTTP. An optional follow-up is to add a private Streamable HTTP endpoint or an authenticated compatibility bridge, keeping existing clients intact. Do not expose internal RAG documents to all users of the public chat instance.

## Product fit and filesystem access

Open WebUI is a leading general-purpose self-hosted chat UI, not a demonstrated market-share leader. On November 18, 2026, GitHub reported roughly [159k stars for Open WebUI](https://api.github.com/repos/open-webui/open-webui) and [47k for LibreChat](https://api.github.com/repos/LibreChat-AI/LibreChat). Stars are a visibility signal, not installations. [LibreChat](https://www.librechat.ai/docs/features/mcp) is a credible alternative when reusable agents and per-agent tool selection are central. [OpenCode Web](https://opencode.ai/docs/cli/web/) is a coding-first UI backed by an agent server; [OpenHands](https://github.com/OpenHands/docs/blob/main/openhands/usage/sandboxes/docker.mdx) is more directly aimed at isolated coding tasks. Neither solves a gap for ordinary two-model chat on NAS.

| Need | Approach |
| --- | --- |
| Inspect selected documents | Upload files or attach a read-only MCP service that exposes a bounded data source. Upload/retrieval is not live filesystem access and retrieval may use an embedding model. Keep a file-search MCP implementation independent of paid inference if the subscription-only constraint applies to all inference. |
| Let the chat model read, edit and run tests | Connect [Open Terminal](https://docs.openwebui.com/features/open-terminal/advanced/security/) to an isolated workspace. The WebUI chat model remains the agent; tool calls run on the terminal side. A UI-visible file root or start directory is not a filesystem sandbox. |
| Run Pi itself from the browser | The [coding-agent integration](https://docs.openwebui.com/features/open-terminal/coding-agents/) launches a separate Pi process via [native RPC](https://github.com/open-webui/open-terminal), not ACP. Pi's own provider/model config controls inference, independently of WebUI's LiteLLM connection. Use a separately restricted LiteLLM key with the same two aliases. The current fleet Pi documents `agent_settled`, but compatibility with the packaged launcher, session handling, extension dialogs and approval policy has not been tested. This is not a way to attach to the existing tmux/Matrix session. Open Terminal's [upstream release](https://github.com/open-webui/open-terminal/releases/tag/v0.17.20) was 0.17.20 when checked. |
| Use a workstation's own tools | [Tether](https://docs.openwebui.com/ecosystem/tether/) links a client device; the built-in workspace sandbox is not available on Linux. Running it as the normal Grill login user would give tools that user's authority, not just access to the selected project. |

Recommendation: keep public `chat.bepis.lol` as chat-only with a dedicated LiteLLM key restricted to Sol and Astra. If browser-based coding is useful, pilot Open WebUI 0.13.x plus a private Open Terminal in a Tailnet-only test setup, using an isolated VM or container, one disposable checkout, no personal home directory or Docker socket, and its own two-model key. Test reading, editing, running a benign project test, and reconnecting. If the goal is to resume the *same* existing Pi/tmux/Matrix sessions, keep the current harness instead of adding a second session owner.

No configuration, lockfile, or live changes were made during this review. No authenticated model or feature tests, builds, or deployment were performed.
