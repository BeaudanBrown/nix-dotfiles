# Open WebUI + Pi for remote project work

Research snapshot: 2026-11-18. Source review only, not a phone or deployment test. See [NAS baseline and upgrade review](./open-webui-review.md). Candidate pair: [Open WebUI 0.13.4](https://github.com/open-webui/open-webui/releases/tag/v0.13.4) and [Open Terminal 0.17.20](https://github.com/open-webui/open-terminal/releases/tag/v0.17.20); current NAS WebUI 0.11.4 predates Pi-as-a-model integration.

## What owns what

Phone browser/PWA → private Open WebUI → Open Terminal → Pi RPC process. Pi reads and edits the checkout on the terminal host and sends inference to LiteLLM. Open WebUI owns chats, folders and UI; Git owns code and branches; Open Terminal owns agent process lifecycle; Pi owns agent state on its own disk. The browser does not connect directly to the terminal in the server-connected setup.

- The [tagged Pi adapter](https://github.com/open-webui/open-terminal/blob/v0.17.20/open_terminal/agents/pi.py) discovers models by spawning `pi --mode rpc --no-session` and calling `get_available_models`. For work it supplies `--session-id` with a resume ID or a new UUID. This is actual Pi, not WebUI simulating Pi tools. It discovers the terminal-side Pi's models, not the WebUI connection's allowlist. Give the pilot a dedicated Pi profile and LiteLLM key limited to `sub-gpt-6.2-sol` and `sub-gpt-6.2-astra`; verify the picker and any default/fallback models. The [coding-agent docs](https://docs.openwebui.com/features/open-terminal/coding-agents/) say a missing agent falls back to the default chat model. Keep that default on the same restricted key and test that the UI makes the loss of execution obvious.
- Use persistent storage for the checkout, Pi's session/profile data and WebUI's chat database. A browser reconnect, a subsequent turn, and resuming after a worker restart are different tests. [Tagged agent lifecycle source](https://github.com/open-webui/open-terminal/blob/v0.17.20/open_terminal/agents/sessions.py) keeps detached processes for reconnect, removes them after more than an hour without a peer and without a touch, and shuts them down on server shutdown. That's not a durable background-job guarantee. A phone locking its screen may behave differently from a brief network hiccup; verify it.
- The coding-agent docs distinguish ordinary follow-ups from edit/regenerate/fork: for Pi those operations start over from chat context, and prior file edits remain. A chat fork is not a Git branch or a filesystem rollback. Out of the box this does not discover or take over the existing Pi/tmux/Matrix sessions. Do not point two live systems at the same native session files or writable worktree.

## A workable project layout

- Use one [WebUI folder](https://docs.openwebui.com/features/chat-conversations/chat-features/conversation-organization/) per repo, with a default terminal, working directory and model. These defaults apply to new chats. A folder is a convenience, not an access boundary.
- Use one saved chat per issue. For concurrent issues, explicitly pick a separate Git worktree or checkout per chat before the first prompt. Names like `project / #123 / shorten import time` tie the conversation to its work. One terminal host can serve several trusted disposable checkouts; separate environments when access must actually differ.
- Start on a phone with a narrow request, review the diff, ask for tests, then continue in the same browser chat on desktop. Use Git branches/PRs as the handoff to desktop Pi, not shared writable session files. Keep approval behavior explicit; upstream Pi support is not evidence that this fleet's custom dialogs, Matrix tools, skills or launcher behave identically in RPC.
- [0.13.4](https://github.com/open-webui/open-webui/releases/tag/v0.13.4) offers diff/command cards, Files/Terminal/Git views and optional GitHub integration. For phone review the cards and GitHub are likely more practical than a full PTY; verify on the phone. Do not add a broad GitHub token just to evaluate the UI.

## Mobile and alternatives

[Android PWA installation](https://docs.openwebui.com/getting-started/open-webui-as-app/) is supported, but browser notifications require the app to be open. Optional WebUI notification webhooks can signal completion/failure while away; a relay to the existing [ntfy setup](./ntfy.md) is a follow-up, not a verified drop-in. Send only minimal metadata, not prompts or diffs. Existing Matrix rooms remain the better fit when the goal is messaging an already-running native Pi session or getting mobile notifications without a second project index. See [fleet Pi/tmux tooling](./tooling.md). GitHub issues/PRs can remain the common project/task record across both approaches.

[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) is a relevant desktop-first comparison; its [Remote discussion](https://github.com/deepseek-ai/deepseek-harness/discussions/3778) is a preview signal, not verified parity with the official phone app or existing Pi workflows. If continuity with the *same* desktop harness session is mandatory, compare that workflow directly rather than treating a portable chat history as equivalent.

## Suggested pilot and pass criteria

Keep public `chat.bepis.lol` chat-only. Run a separate Tailnet-only WebUI and a private Open Terminal service in an isolated VM/container, with only disposable checkouts, no host home mount or Docker socket, and a restricted key. An always-on host avoids tying availability to Grill being awake. No Tether or terminal provisioning service is required for this pilot. Verify on the actual phone: two folders route to the correct checkouts; Pi discovers only the intended models; a short benign edit/test continues or fails visibly when the phone locks and switches networks; the completed diff is visible after reconnect; permissions and stop requests work; worker restart leaves changes on disk and reports interrupted runs clearly; no duplicate execution after reconnect. If push notifications or surviving reboots without losing the active run are requirements, treat those as separate go/no-go criteria. No services, credentials, lockfiles, or sessions were changed for this research.
