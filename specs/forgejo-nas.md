# First NAS Forgejo pilot

Before building, provision `forgejo/oidc-client-secret` (a new, random, single-line client secret; e.g. 32 random bytes encoded as hex) and `forgejo/authentik-username` (exact existing Authentik username, not display name) in the NAS SOPS file and update the `sopsSecrets` input. Do not paste values in logs/chat or reuse the Headscale secret. Missing credentials can prevent the shared Authentik worker from starting. Reserve `forgejo-recovery` for local recovery; use a different OIDC username and email.

Keep a working admin session open. Confirm no existing Authentik application/provider uses slug `forgejo`, name `Forgejo` or client ID `nas-forgejo`; the default provider consent/invalidation flows and `authentik Self-signed Certificate` should exist. No manual provider creation, Headscale change or global passkey flow change is needed. Review unrelated worktree changes before deploying the NAS configuration. Build first, then activate with the normal NAS workflow. Expect the Authentik services to reload. The extra CLI build lets the admin command read its secret without putting it in process arguments.

## Acceptance after activation

- Check `systemctl status forgejo authentik-worker` and the Authentik blueprint instance **NAS - Forgejo OIDC**. It must report successful application. If startup raced discovery, confirm the blueprint succeeded before retrying `forgejo.service`. On credential rotation explicitly reapply the blueprint: restarting the worker alone does not change the blueprint file hash.
- From a tailnet client, open `https://git.bepis.lol`, use **authentik**, and complete the existing passkey flow. Verify an ordinary second identity cannot obtain access and unauthenticated visitors cannot read or register. From off-tailnet confirm the public NAS ingress cannot serve this hostname even when its address is supplied explicitly.
- On NAS, privately retrieve `/var/lib/forgejo/initial-recovery-login` as root; it contains a generated initial password. Log in as `forgejo-recovery` in a separate browser, change the password, store it in your password manager and remove the initial receipt. Startup does not reset an existing recovery password. Do not send the receipt to an agent or terminal recording.
- Create a disposable private repository. Use a repo-scoped Forgejo token via a credential helper for HTTPS Git, not an Authentik password. Push a branch and a small LFS object and clone them in a fresh checkout. Test a PR. No runner or deployment credentials are configured. The shared proxy limits individual uploads to 200 MiB.
- Git SSH uses Forgejo's own listener on the NAS tailnet address and allocated `forgejo/ssh` port, not NAS OpenSSH. After the **NAS - Forgejo OIDC** blueprint succeeds, complete a fresh Authentik login as `beau`. Compare the SSH key fingerprints in Forgejo to the public keys on grill, t480 and nas (`ssh-keygen -lf ~/.ssh/id_ed25519.pub`). From each, test `git ls-remote` with the SSH clone URL shown on a private test repo; verify the server host-key fingerprint independently on NAS before trusting it. Test that an unlisted identity cannot clone and the SSH port is unreachable off-tailnet.
- On rotation, reload the worker credentials, explicitly reapply the blueprint and sign in again. Verify the replacement works and the old key is rejected using a single explicit identity (`IdentitiesOnly=yes`). For urgent revocation remove the compromised key from Forgejo too; do not wait for the next login. HTTPS Git is independent.
- Verify a fresh Headscale login without signing out of the existing session. A Nix rollback does not revert database state, blueprint objects or Forgejo migrations. Keep important repositories canonical elsewhere until backups have been addressed.

## DSH access and portable Forgejo host key

- The NAS SOPS file needs two separate entries: `forgejo/dsh-ssh-public-key` (the existing DSH **login** public key, imported for `beau`) and `forgejo/ssh-host-ed25519-private-key` (Forgejo's **server** private key, loaded only by Forgejo). Update the `sopsSecrets` flake input from a trusted checkout before deploying NAS. Do not share the private host key with clients or put it in Authentik.
- Deploy NAS first. Verify that both the existing RSA host key and the new Ed25519 host key are still served. From an already trusted NAS session, check the Ed25519 fingerprint with `ssh-keyscan -T 5 -p 12595 -t ed25519 git.bepis.lol 2>/dev/null | ssh-keygen -E sha256 -lf -` and compare it with the fingerprint recorded when the keypair was generated. Use the verified public host key for the DSH pin; do not trust a scan by itself.
- Reapply the **NAS - Forgejo OIDC** blueprint and sign in to Forgejo again as `beau` to import the DSH login key. DSH also needs a separate signer update on grill: retain the GitHub pin and allow the existing DSH identity for Forgejo only against the verified host key. No API token is needed for Git over SSH.
- After deploying the grill update, check both hosts from DSH with `git ls-remote` on an authorized repository. On a disposable Forgejo repository, verify push access if needed. On a future Forgejo move, grant the new host SOPS access to the same host private key and keep the DNS name and SSH port; clients that pin that Ed25519 key will not need a new pin.
